# LLM synthesis of automation workflows and programs with verification (related work for GOV-AIOS Studio)

Verification legend: **[V]** = arXiv ID, URL and the stated claims were confirmed in this session's searches or fetches (the abstract, the arXiv listing or the primary page). **[M]** = arXiv ID recalled from memory and not re-fetched this session; check it before citing. **[S]** = the claim comes only from secondary or aggregator summaries. Numbers marked [S] should be checked against the PDF.

Studio, in short: a one-sentence request leads to a read-only AX-tree capture. Personal text is masked: control names are kept, and row and cell text becomes `‹text n›`. A tool-less LLM receives a closed DSL schema plus two examples and returns YAML flow and page files. A deterministic verifier then checks the output: element resolution against the capture, a risk floor that can only be raised, permissions trimmed to the actions actually used, and destinations limited to captured origins. On failure it retries up to 3 times with error feedback. The flow then test-runs as a draft capped at navigate risk, and a human approves it with Touch ID.

## Q1. LLM-generated web/UI automation scripts, RPA, and workflow induction

### Takeaway
Prior work produces automations in three ways: (a) an LLM writes a workflow program from an instruction (ProAgent, WorkflowLLM, UiPath Autopilot, Power Automate Copilot); (b) an agent induces reusable workflows or skills from its own trajectories (AWM, ASI, SkillWeaver); or (c) a model learns from demonstrations (ECLAIR). Their validation checks *functional success*: execution feedback, test trajectories, a reward model or an evaluator. None treats the generated artifact as untrusted input to be checked against a security policy (element provenance, a risk floor, least privilege, origin allow-listing) before a human signs it. That gap is the one Studio fills.

### Cited Findings
**Instruction-to-workflow generation (RPA lineage)**
- **ProAgent** (Ye et al., Tsinghua/OpenBMB; arXiv:2311.10751, Nov 2023, marked "work in progress") [V]. It proposes "Agentic Process Automation" (APA), in which an LLM agent *generates the workflow* from a human instruction and also handles the dynamic decision steps at run time. Workflows are written in an "Agentic Workflow Description Language" built from JSON structure plus Python code, chosen so the LLM can easily read and write them. Experiments used GPT-4-0613 (per the repo README). Validation: the workflow is executed, and LLM "DataAgent/ControlAgent" nodes make decisions inside it. I found no static verification of the generated workflow and no privacy handling. **Difference:** ProAgent *embeds* LLM judgment inside the running workflow. Studio removes the LLM from run time entirely: the flow is a closed DSL with no free-form code, and the LLM is used only at authoring time, without tools. — [arXiv](https://arxiv.org/abs/2311.10751v2)
- **WorkflowLLM** (Fan et al.; arXiv:2411.05451, Nov 2024, cs.SE) [V]. It takes a data-centric, fine-tuning approach to "workflow orchestration". WorkflowBench contains 106,763 workflows covering 1,503 APIs across 83 apps, mostly collected from Apple Shortcuts. Shortcuts average 70.4 actions, and the paper reports that GPT-4o struggles at this length. The fine-tuned WorkflowLlama outperforms the baselines, and the authors report zero-shot generalisation to T-Eval. Validation and metrics are CodeBLEU and an LLM-judged "Pass Rate", so correctness is similarity- or judge-based, not checked by a deterministic verifier. Privacy is not addressed. **Difference:** Studio's output is accepted only if a deterministic verifier passes it against a live capture. An LLM judge or BLEU similarity is not used as an acceptance criterion. — [arXiv](https://arxiv.org/abs/2411.05451v1); [HF](https://huggingface.co/papers/2411.05451)
- **UiPath Autopilot** (vendor) [V for the doc wording]. The docs say it lets users "create automations, tests, or app interfaces from a single natural language prompt" and can "interpret your requests, convert them to workflows or applications, and suggest fixes". At its 2023 launch it was described as "text-to-workflow", plus text-to-expression and text-to-code in Studio ([S] via KMWorld and CX Today). Validation is the developer's review in the Studio designer. The governance and permission model of generated workflows is not described in the pages found. — [UiPath docs](https://docs.uipath.com/autopilot/other/latest/user-guide/about-autopilot); [KMWorld](https://www.kmworld.com/Articles/News/News/UiPaths-Autopilot-blends-AI-and-automation-for-enhanced-workflow-productivity--161101.aspx); [CX Today](https://www.cxtoday.com/data-analytics/uipaths-new-autopilot-turns-paper-documents-into-automation-apps/)
- **Microsoft Power Automate for desktop, Copilot** (vendor) [V]. Users can "create a new flow or add more steps to an existing flow by just describing what you want to achieve using natural language prompts", and Copilot inserts actions at the end or under the selected action. The Learn page labels it a preview powered by Azure OpenAI, with flow creation listed for the US only at the time of the snapshot. A separate "Record with Copilot" feature (PAD 2.48+, work or school accounts only) builds desktop flows from a recording, which is the demonstration route. Validation is the user's review in the designer. No pre-acceptance policy check of generated actions is documented. — [MS Learn: Copilot in PAD](https://learn.microsoft.com/en-us/power-automate/desktop-flows/copilot-in-power-automate-for-desktop); [Release plan 2024 wave 1](https://learn.microsoft.com/en-us/power-platform/release-plan/2024wave1/power-automate/create-desktop-flows-using-natural-language-copilot-power-automate-desktop)

**From demonstrations**
- **ECLAIR** — "Automating the Enterprise with Foundation Models" (Wornow, Narayan, Opsahl-Ong, McIntyre, Shah, Ré, Stanford; arXiv:2405.03710; PVLDB 17, 2024, DOI 10.14778/3681954.3681964) [V for metadata, S for details]. Multimodal FMs (GPT-4) learn enterprise workflows from demonstrations and natural-language SOPs with minimal supervision. The paper motivates this with RPA's high setup cost, low initial accuracy and heavy maintenance, and pitches near-instant setup in contrast to brittle scripted bots. Its stages are demonstrate, execute, and validate (self-monitoring of completion). I did not open the PDF, so the result numbers are unverified. Privacy: the demonstrations are screenshots or video sent to GPT-4V, and I found no masking. **Difference:** ECLAIR's "validate" step checks whether the task got done. Studio validates the *artifact* against security invariants before it is ever run outside draft mode. — [arXiv](https://arxiv.org/abs/2405.03710); [Crossref](https://api.crossref.org/works/10.14778%2F3681954.3681964)

**Workflow/skill induction from agent experience**
- **Agent Workflow Memory (AWM)** (Wang, Mao, Fried, Neubig; arXiv:2409.07429, Sep 2024) [V]. It induces reusable natural-language/text "workflows" from past trajectories and feeds them back into the agent's memory, offline or online. On WebArena it improves over the BrowserGym baseline by +12.0 absolute points (51.1% relative) in success rate with fewer steps. On Mind2Web it gives +24.6% relative step-wise success in cross-task evaluation, and the gains hold cross-website and cross-domain. Validation in the online setting uses an LLM evaluator to filter for successful trajectories before induction. Privacy is not addressed. **Difference:** AWM's workflows are *soft prompts* that the agent may follow or ignore. Studio's flows are executable, closed-DSL artifacts that a policy engine enforces. — [arXiv](https://arxiv.org/abs/2409.07429)
- **Agent Skill Induction (ASI)**, "Inducing Programmatic Skills for Agentic Tasks" (Wang, Gandhi, Neubig, Fried, CMU; arXiv:2504.06821; COLM 2025) [V]. It induces *executable program* skills (e.g. `search_product(name)`) from trajectories, and **verifies each skill by re-executing it on test trajectories before adding it to the action space**. On WebArena it beats the static baseline by 23.5% and AWM by 11.3% in success rate, and uses 10.7–15.3% fewer steps. Skills partially transfer to redesigned sites. **Difference:** this is the closest "LLM writes, execution checks" precedent, but its check is *functional* (does it reproduce success?). Studio's check is *security*: are the element provenance, risk floor, least privilege and origins all within bounds? Studio also adds a human signature step. — [arXiv](https://arxiv.org/abs/2504.06821)
- **SkillWeaver** (Zheng et al., OSU/CMU; arXiv:2504.07079, Apr 2025) [V]. The agent explores a site, proposes skills, synthesises them as Python/Playwright "APIs", and *hones* them by testing and debugging against environment feedback and a reward model. Relative success gains are reported as +31.8% on WebArena and +39.8% on real sites (arXiv abstract). Some summaries give a 25–38% range [S, conflicting], so cite the abstract figure. APIs from strong agents boost weaker agents by up to 54.3% on WebArena. The skills are arbitrary Python, unsandboxed, with no permission model. **Difference:** SkillWeaver's output is Turing-complete code accepted after functional testing. Studio confines the LLM to a closed, non-Turing-complete DSL so that static checks (element resolution, permission trimming) are *decidable*. — [arXiv](https://arxiv.org/abs/2504.07079v1)
- **WorkArena** (Drouin et al., ServiceNow; arXiv:2403.07718; ICML 2024) [V]. An enterprise knowledge-work benchmark on ServiceNow (33 tasks / 19,912 instances in v4–v5; v1 said 29 / 23,150), together with the BrowserGym environment. ServiceNow's blog reported that the best agent of that time reached about 55% success while being slow and costly. WorkArena++ (arXiv:2407.05291 [M]) extends it to compositional workflows. It is relevant as an evaluation setting for enterprise flows, not as a synthesis method. — [arXiv v5](https://arxiv.org/html/2403.07718v5); [PMLR](https://proceedings.mlr.press/v235/drouin24a.html); [ServiceNow blog](https://www.servicenow.com/blogs/2024/introducing-workarena-benchmark)

**Page representations (DOM / AX tree vs screenshot)**
- **Mind2Web** (Deng et al.; arXiv:2306.06070 [M]; NeurIPS 2023 D&B). 2,000+ tasks over 137 real sites. It uses cleaned-HTML/DOM observations with a small-LM candidate-element ranker before the LLM picks an element. That pruning is a precedent for Studio sending a reduced tree. — [arXiv](https://arxiv.org/abs/2306.06070)
- **WebArena** (Zhou et al.; arXiv:2307.13854 [M]; ICLR 2024). A self-hosted, realistic web environment that uses the **accessibility tree** as its default text observation. Its GPT-4 baseline was about 14% task success versus about 78% for humans [M, from memory]. — [arXiv](https://arxiv.org/abs/2307.13854)
- **OSWorld** (Xie et al.; arXiv:2404.07972; NeurIPS 2024) [V]. In the original baseline, screenshot-only agents scored about 5.3%, while a11y-tree agents ranged from about 2.4% to 12.2% across models. The authors still argue that screenshot-only is the long-term goal, because AX trees are not always available. [S, numbers via search summary] — [arXiv PDF](https://arxiv.org/pdf/2404.07972)
- **OS-Harm** (arXiv:2506.14866) [S]. On the OSWorld small set with Gemini 2.5 Pro: a11y-only 21.1%, screenshot-only 5.3%, combined 25.6%. **OSWorld-Human** (arXiv:2506.16042) [S] finds the AX tree "drastically increases per-task latency" because it adds thousands of tokens per step. — [OS-Harm](https://arxiv.org/pdf/2506.14866); [OSWorld-Human](https://arxiv.org/pdf/2506.16042)
- **SeeAct** (Zheng et al.; arXiv:2401.01614 [M]; ICML 2024). GPT-4V can act as a web agent "if grounded". Grounding (mapping a described action to an element) was the main bottleneck, and grounding through HTML element choices beat pure image grounding [M]. **Aria-UI** (arXiv:2412.16256) [S] reports 15.15% OSWorld success with GPT-4o planning plus pixel grounding. — [SeeAct](https://arxiv.org/abs/2401.01614); [Aria-UI](https://arxiv.org/pdf/2412.16256)

### Inferences
- Studio's AX-tree choice fits the evidence that text trees ground better than raw pixels for current LLMs. Using the tree only *once, at authoring time*, also avoids the per-step latency cost that OSWorld-Human documents. Unlike every run-time agent above, Studio needs no screenshot at run time.
- The induction line (AWM → ASI → SkillWeaver) shows a clear trend from text hints to verified executable code. Studio can present itself as the next step on that line: from *functionally verified* to *security-verified and human-signed*.
- The vendor copilots (UiPath, Power Automate) set the industry baseline: NL to a workflow, then human review in a designer. Studio's contribution is to make that review step mechanical where it can be (verifier) and attested where it cannot (Touch ID).

### Gaps
- I did not open the PDFs of ECLAIR, Mind2Web or WebArena, so their result numbers are unverified or recalled from memory.
- I could not find public documentation of how UiPath Autopilot or Power Automate Copilot *validate* generated actions beyond human review, or what screen or tenant data they send to Azure OpenAI. Treat "no automated policy check" as *absence of evidence*.
- I did not check WorkflowLLM's exact Pass Rate numbers.

## Q2. Constrained / verified generation and LLM-generated security policies

### Takeaway
Two mature lines bracket Studio. *Grammar-constrained decoding* guarantees syntax but needs control over the decoder, and recent work shows that grammars can themselves be attack surfaces. *LLM-generates / deterministic-checker* frameworks (Clover in program synthesis; Conseca, Progent, GuardAgent and CaMeL in agent security) keep the LLM out of the trusted computing base. Studio applies the second pattern to *authoring* rather than to run-time tool calls. It also checks artifacts against an observed environment snapshot (the captured AX tree and origins), not only against a schema.

### Cited Findings
**Grammar/DSL-constrained decoding**
- **SynCode** (Ugare et al.; arXiv:2403.01632) [V]. A DFA "mask store" built offline from a CFG, claimed sound and complete for the grammar. The authors report that it eliminates JSON syntax errors and cuts Python and Go syntax errors by about 96% (self-reported). — [arXiv](https://arxiv.org/abs/2403.01632v4)
- **XGrammar** (Dong et al.; arXiv:2411.15100) [V]. It splits tokens into context-independent ones (checked ahead of time) and context-dependent ones, using a byte-level PDA. It claims up to 100x lower per-token CFG latency and up to 80x end-to-end speedup, and says it is suitable for DSLs. — [arXiv](https://arxiv.org/html/2411.15100v3)
- **Outlines / "Efficient Guided Generation"** (Willard & Louf; arXiv:2307.09702 [M]) and **Grammar-Constrained Decoding for structured NLP** (Geng et al.; arXiv:2305.13971 [M]; EMNLP 2023) are earlier formulations based on FSMs and grammars. — [Outlines](https://arxiv.org/abs/2307.09702); [Geng](https://arxiv.org/abs/2305.13971)
- **"When Grammar Guides the Attack"** (arXiv:2503.24191) [S, title and ID from the search listing only]. It argues that structured-output grammars open control-plane jailbreak vectors. This is a caution against treating constrained decoding as a *security* control. — [arXiv](https://arxiv.org/pdf/2503.24191)

**LLM generates, verifier checks (program synthesis)**
- **Clover** (Sun, Sheng, Padon, Barrett; arXiv:2310.17807; SAIV 2024) [V]. The LLM produces code, docstrings and Dafny annotations, and a closed-loop *consistency check* among the three filters out bad code. It accepts up to 87% of correct CloverBench instances with **zero false positives**, and found 6 incorrect programs in MBPP-DFY-50. — [arXiv](https://arxiv.org/abs/2310.17807)
- **Self-Debugging** (Chen et al.; arXiv:2304.05128 [M]; ICLR 2024). The LLM repairs code using execution feedback and explanations. It is the standard precedent for Studio's "retry ≤3 with verifier errors" loop. — [arXiv](https://arxiv.org/abs/2304.05128)

**LLM-generated security policies with deterministic enforcement**
- **Conseca**, "Contextual Agent Security: A Policy for Every Purpose" (Tsai & Bagdasarian, Google; arXiv:2501.17070; HotOS 2025; v1 titled "Context is Key in Agent Security") [V]. An LLM generates *just-in-time, contextual, human-verifiable* policies from **trusted context only**, and enforcement is deterministic. The authors argue this makes the system "impervious" to prompt injection, because untrusted content (e.g. an email) never reaches the policy generator. The prototype is a Linux computer-use agent. **Difference:** Conseca's policy generator sees only trusted context. Studio's generator *must* see untrusted page structure, so Studio compensates in two ways: it masks row and cell text, and it lets a verifier *trim* permissions and *floor* risk independently of what the LLM claims. — [arXiv](https://arxiv.org/abs/2501.17070)
- **Progent** (Shi, He, Wang, Wu, Li, Guo, Song; arXiv:2504.11703, v2 Aug 2025) [V]. A DSL for fine-grained tool-call privilege policies, enforced deterministically during execution and modular with respect to agent internals. **LLMs can generate and update the policies** automatically, and the authors report this yields effective least privilege. Evaluated on AgentDojo (and others), it reports a large reduction in attack surface while keeping utility [S for exact numbers]. **Difference:** Progent's LLM writes *policies for an agent* that keeps acting with an LLM in the loop. In Studio, the LLM writes the *program itself*, and the verifier *derives* permissions from the actions the program actually uses. Studio does not trust LLM-proposed permissions at all, which is closer to static least-privilege inference. — [arXiv](https://arxiv.org/abs/2504.11703v2)
- **CaMeL**, "Defeating Prompt Injections by Design" (Debenedetti, Shumailov et al., Google/ETH; arXiv:2503.18813) [V for the idea]. A privileged LLM turns the *trusted* user query into a program. A custom Python interpreter tracks capabilities (provenance plus allowed readers) on every value and enforces policies, while a quarantined LLM parses untrusted data without tool access. AgentDojo results are reported as 67% of tasks solved with provable security (abstract) or 77% versus 84% undefended (a later summary) [conflicting across versions]. **Difference:** this is the closest architectural cousin, since both use an LLM to write a program that a deterministic runtime then constrains. CaMeL generates *per query at run time* and tracks data flow dynamically. Studio generates *once*, verifies statically against a captured tree, and has a human sign it, so run time involves no LLM. — [HF/abstract](https://huggingface.co/papers/2503.18813)
- **GuardAgent** (Xiang et al.; arXiv:2406.09187; ICML 2025) [V for metadata, S for numbers]. A guard LLM plans, then *generates guardrail code* that an interpreter runs deterministically to allow or deny the target agent's actions. It reports about 98% accuracy on EICU-AC and about 83% on Mind2Web-SC. ShieldAgent (arXiv:2503.22738) [S] reports +11.3% over it. — [arXiv](https://arxiv.org/abs/2406.09187); [PMLR](https://proceedings.mlr.press/v267/xiang25a.html)
- **AgentSpec** (arXiv:2503.18666 [M]) is a DSL for run-time rules on LLM agents. Its ID was not confirmed this session.

**Least-privilege inference**
- **CELLMATE**, "Sandboxing Browser AI Agents" (arXiv:2512.12594, Dec 2025) [S]. It predicts which web apps a prompt needs and selects the minimal policy set per app. It is deny-by-default and rejects under-specified prompts. — [arXiv PDF](https://arxiv.org/pdf/2512.12594)
- **"Do Coding Agents Understand Least-Privilege Authorization?" / AuthBench** (arXiv:2605.14859) [S, **unverified**: seen only on aggregator pages]. Frontier models both omit permissions the task needs and over-grant unused or sensitive ones. A two-phase "generous, then audit each entry" method reportedly improves sensitive-task success by up to 15.8%. — [aggregator](https://awesomepapers.io/papers/2605.14859)

### Inferences
- Studio takes a hybrid position. It uses a closed DSL like the constrained-decoding line, but enforces the schema *after* generation, so it works with any hosted model (no logit access). It uses a verifier like Clover, but the specification is a *security* spec plus an *environment snapshot*. Its permissions come from deterministic analysis of the produced program, not from the LLM. The AuthBench finding (if verified) that LLMs both under- and over-grant directly motivates that last choice.
- Studio's "risk can only go up" rule is a monotone lattice constraint: the verifier takes the maximum of the LLM's label and a floor computed from role and name. I found no prior paper that frames LLM-labelled risk this way. This is a candidate novelty claim, to be stated carefully.
- Origin allow-listing against *captured* origins means the program's reach is bounded by what the human actually visited. This resembles Conseca's "trusted context" but is grounded in observation rather than in a task description.

### Gaps
- I did not verify Progent's exact AgentDojo numbers, which version of CaMeL's 67% vs 77% is current, or AgentSpec's ID.
- I found no paper that verifies LLM-generated *UI automation* programs against a captured accessibility tree. That absence could be a novelty claim, but the search was not exhaustive (e.g. UIST/CHI programming-by-demonstration work, or ICSE work on test-script generation such as LLM-generated Selenium/Appium scripts, was not surveyed).

## Q3. Privacy-preserving UI understanding before cloud LLMs

### Takeaway
A 2026 cluster of papers puts a trusted local layer between the screen and a cloud GUI agent that replaces PII with placeholders. They show that naive span-masking leaks fragmented PII and breaks entity continuity. Studio's masking is structurally simpler and stronger in one respect: it masks *by AX role* (all row and cell text), not by PII detection. This avoids detector recall failures (the PlanTwin critique of regex/NER), at the cost of the LLM never seeing the data content. That trade-off is acceptable because Studio authors *structure*, not content.

### Cited Findings
- **Anonymization-Enhanced Privacy Protection for Mobile GUI Agents: "Available but Invisible"** (arXiv:2602.10139) [S]. A trusted local layer runs a local LLM that rates sensitivity, asks the user for permission, and gives the cloud agent placeholders only. It also cites **PrivWeb**, which anonymises PII in the DOM before the agent sees it [S, PrivWeb not located directly]. — [arXiv](https://arxiv.org/html/2602.10139v1)
- **PrivacyGuard** (Yuan & Li; arXiv:2610.16778, 12 Oct 2026) [V]. It argues that "existing placeholder defenses mask detected spans and reuse exact strings", so fragmented or altered forms leak or lose continuity. It proposes source-linked sanitisation (SAN) and locally resolvable references (REF) "without returning raw values to the upload path". Results: 34–83% less audited leakage than the nearest prior pipeline, cross-form continuity rising from 0.04 to 0.81, Android reference tasks rising from 8/30 and 7/30 to 17/30 and 20/30, and about 62.7% less field exposure on PrivScreen. — [arXiv](https://arxiv.org/abs/2610.16778)
- **CAPED: Context-Aware Privacy Exposure Defense for Mobile GUI Agents** (arXiv:2606.12666) [S]. It redacts screenshots with overlays and typed placeholders such as `[PERSON_1]`, and the user can approve temporary reveals. — [arXiv](https://arxiv.org/pdf/2606.12666)
- **PlanTwin** (arXiv:2603.18377) [S]. It plans privately for cloud-assisted agents through abstractions, and argues that regex/NER tools such as Presidio miss domain identifiers, embedded secrets and structural cues. — [arXiv](https://arxiv.org/pdf/2603.18377)
- **LLM-Redactor** (arXiv:2604.12064) [S]. An empirical comparison of eight techniques finds that none dominates. Local routing is best for PII, and redaction plus rephrasing keeps exact PII leaks at or below 7% for requests that must go to the cloud. — [arXiv](https://arxiv.org/html/2604.12064v1)
- **PII Shield** (arXiv:2603.24895) [S]. A browser overlay that redacts prompts and attachments locally before they go to the cloud LLM. — [arXiv](https://arxiv.org/html/2603.24895v1)
- **Apple Private Cloud Compute** (Apple Security blog, 10 Jun 2024) [V]. Its five core requirements: "Stateless computation on personal user data", "Enforceable guarantees", "No privileged runtime access", "Non-targetability", "Verifiable transparency" (published images plus a transparency log). In 2026 it was reportedly extended to Google Cloud hardware with an append-only hardware ledger [S]. — [Apple](https://security.apple.com/blog/private-cloud-compute/); [Help Net Security](https://www.helpnetsecurity.com/2026/06/10/apple-private-cloud-compute-google-cloud-expansion/)

### Inferences
- **Positioning against PCC:** PCC protects data *in* the cloud through attested, stateless servers. Studio instead *minimises what leaves the device* (masked structure only) and needs no trust in the LLM provider for confidentiality of row data. The two are complementary, not competing.
- **Positioning against the mobile-agent masking line:** those systems mask *at every run-time step* and must resolve placeholders back to real values so the agent can act. That resolution step is exactly where PrivacyGuard finds leaks. Studio masks *once at authoring time*. The run-time executor is deterministic and local, so placeholders never need to round-trip through the LLM. This is a structural advantage, and worth stating explicitly.
- **Residual risk:** control names (button labels, headings, sometimes folder names rendered as controls) remain unmasked, and on some pages they carry personal data such as a user's name in an account button. The paper should acknowledge this. PlanTwin's critique of structural cues applies.

### Gaps
- PrivWeb was not located as a primary source. I did not verify the numbers in 2602.10139, CAPED, PlanTwin or LLM-Redactor beyond the abstracts in search snippets.
- I found no paper that masks *by accessibility role* (as opposed to by PII detection) before an LLM call. This is likely novel, but unconfirmed.

## Q4. Risks specific to LLM-authored automations: injection into the generated program, over-permissioning

### Takeaway
Indirect prompt injection through page content is well established for *run-time* agents. Agents frequently start executing injected instructions, though they often fail to complete them ("security by incompetence"). For *authored* automations the threat shifts: injected page text can steer the *generated program*, which then runs repeatedly without an LLM in the loop, so a successful injection is persistent. Studio's defences line up with this threat. Masking row and cell text removes most attacker-controlled text from the prompt. Element resolution prevents fabricated targets. Destinations limited to captured origins block exfiltration endpoints. Permission trimming prevents over-grant. The draft cap at navigate risk and Touch ID approval bound the blast radius.

### Cited Findings
- **Indirect prompt injection** foundation: Greshake et al., "Not what you've signed up for" (arXiv:2302.12173 [M]; AISec 2023). — [arXiv](https://arxiv.org/abs/2302.12173)
- **WASP** (Evtimov et al., Meta FAIR; arXiv:2504.18575; NeurIPS 2025 poster) [V]. A sandboxed VisualWebArena-based benchmark. Agents *begin* executing injected instructions 16–86% of the time but achieve the attacker goal only 0–17% of the time, which the authors call "security by incompetence". Simple human-written injections fool even reasoning models. — [arXiv](https://arxiv.org/abs/2504.18575v3)
- **AgentDojo** (Debenedetti et al.; arXiv:2406.13352 [M]; NeurIPS 2024 D&B) is the standard tool-agent injection benchmark used by CaMeL and Progent. **EIA**, Environmental Injection Attack on generalist web agents (Liao et al.; arXiv:2409.11295 [M]), injects hidden elements into pages to steal PII. **BrowseSafe** (arXiv:2511.20597) [S] provides HTML-embedded injections plus a layered defence. — [AgentDojo](https://arxiv.org/abs/2406.13352); [EIA](https://arxiv.org/abs/2409.11295); [BrowseSafe](https://arxiv.org/html/2511.20597v1)
- **Over-permissioning:** Progent frames over-privileged tool access as the root cause of agent attacks [V] ([arXiv](https://arxiv.org/abs/2504.11703v2)). AuthBench reports that LLMs both over- and under-grant permissions [S, unverified] ([aggregator](https://awesomepapers.io/papers/2605.14859)). SkillWeaver and ASI emit unsandboxed Python/Playwright skills with no permission model [V for the design] ([SkillWeaver](https://arxiv.org/abs/2504.07079v1), [ASI](https://arxiv.org/abs/2504.06821)).
- **Persistence:** AWM, ASI and SkillWeaver store induced workflows or skills for reuse [V] ([AWM](https://arxiv.org/abs/2409.07429)), so a poisoned trajectory would turn into a persistent poisoned skill. I found no paper that explicitly evaluates *injection into induced skills or workflows*.

### Inferences
- Mapping Studio's checks to threats:
  - Injected text asks the LLM to add a step that clicks a hidden or fake element → **element-must-resolve in capture**.
  - The LLM labels a destructive click as "read" → **risk floor by role and name; risk only raised**.
  - The generated flow requests write or send permissions it does not use → **permission trimming**.
  - The flow navigates to an attacker URL → **destination ∈ captured origins**.
  - The flow is logically wrong but policy-valid → **draft run capped at navigate risk plus Touch ID approval**.
- The remaining injection channel is *unmasked control names*: an attacker who controls a button label or heading can still address the LLM. Every action the injection could cause is still bounded by the verifier invariants. Injection can at worst produce a *wrong but in-policy* flow, which the human must catch at approval. This deserves an explicit evaluation (e.g. seed WASP/EIA-style payloads into control names and measure verifier rejections versus reaching approval).
- WASP's "security by incompetence" does not carry over to authored flows. Once a deterministic executor runs an injected step, it executes it competently every time. This argues that static verification matters *more* for synthesis than for run-time agents.

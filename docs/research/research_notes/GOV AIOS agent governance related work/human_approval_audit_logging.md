# Human-in-the-loop approval of agent actions, presence-bound authorization, and tamper-evident audit logging (related work for GOV-AIOS)

Verification legend: items marked **[V]** were checked against the primary or indexing source during this research session (2026-11-06). Items marked **[U]** come from the researcher's prior knowledge or secondary sources only. Their URL/DOI was not re-fetched this session, so the writer must check them before citing.

## Q1. Human oversight of agents: HITL confirmation for LLM agents, approval/consent fatigue and warning habituation, MFA push-fatigue attacks

### Takeaway
The best 2025–2026 evidence on approval rates comes from vendor telemetry, not controlled user studies. Anthropic reports that Claude Code users accept 93% of manual permission prompts, and it explicitly names "approval fatigue" as the reason it moved to sandboxing and classifier-based auto mode. That telemetry agrees with a decade of usable-security work: warning habituation is automatic (fMRI), most users ignore install-time permissions, and click-through depends on UI design. The Uber 2022 breach shows that a repeated low-friction approval prompt is an exploitable attack surface. GOV-AIOS's exponential backoff after refusals and its biometric-per-run gate respond to exactly this finding.

### Cited Findings

**Agent-specific HITL telemetry and critiques (2025–2026)**
- **[V]** Anthropic, "Claude Code auto mode" (engineering blog, 25 Mar 2026): "in practice users accept 93% of them anyway" (manual permission prompts). It defines approval fatigue as people who "stop paying close attention to what they're approving." Auto mode stops the model and escalates to the human after "3 consecutive denials or 20 total" in a session. Headless mode terminates instead. The classifier's false-negative rate on real overeager actions is 17% (n=52, two-stage pipeline). On synthetic exfiltration it is 5.7% (n=1,000). The false-positive rate is 0.4% end to end on about 10k real tool calls. The authors say it "is not a drop-in replacement for careful human review on high-stakes infrastructure." — [Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)
- **[V]** Anthropic, "Claude Code sandboxing" (20 Oct 2025): "sandboxing safely reduces permission prompts by 84%" in internal usage. Constant approve-clicking leads to "approval fatigue," which makes development less safe. — [Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)

**MFA push fatigue as the closest analogue**
- **[V]** Uber security update (Sept 2022). The attacker had a contractor's password. Each login triggered a 2FA approval request until "Eventually, however, the contractor accepted one." Uber believes the attacker was affiliated with Lapsus$ (attribution not confirmed). — [Uber Newsroom](https://www.uber.com/newsroom/security-update/)
- **[V]** NIST SP 800-63B-4 (final, July 2025), §3.1.3. Approve/deny-only out-of-band push "is no longer considered acceptable" because users may approve without comparing secrets. - **[V, title/venue only]** Jubur, Shrestha, Saxena, Prakash, "Bypassing Push-based Second Factor and Passwordless Authentication with Human-Indistinguishable Notifications," AsiaCCS 2021, pp. 447–461. The prompt's attribution to "Shirvanian" is wrong. The findings were not read this session. — [researchr](https://researchr.org/publication/JuburSSP21); [PDF](https://nsaxena.engr.tamu.edu/wp-content/uploads/sites/238/2023/10/3433210.3453084.pdf)

### Inferences
- GOV-AIOS's exponential backoff after repeated refusals is the agent-side equivalent of the SP 800-63B-4 §3.1.3.2 push rate limit and of Claude Code's "3 consecutive / 20 total denials, then escalate" rule. Each one limits how many prompts an adversary or a looping agent can generate. One design point is worth stating in the paper. In NIST, generating a new secret "SHALL NOT reset the failed authentication count." GOV-AIOS should likewise not let a fresh request reset the backoff.
- Touch ID per agent run, rather than per tool call, cuts prompt volume, which the habituation literature says matters. But a constant-looking biometric sheet is exactly the "static warning" that Anderson et al. show habituates. The paper should state that the prompt text (the flow name plus digest/code) varies per request, a weak form of polymorphism.
- Lies-in-the-Loop shows that when the agent writes the approval text, approval is not a security boundary. GOV-AIOS's advantage is that the prompt content is generated by the governance layer from the flow file digest, not by the model. The paper should claim this explicitly.

### Gaps
- No controlled user study was found (2023–2026) that measures how often users approve harmful LLM-agent actions shown in a confirmation prompt. The evidence is vendor telemetry (93%) and position papers. This could be a contribution or limitation for the paper.
- The OpenAI Operator system card returned HTTP 403. Its confirmation-recall numbers could not be verified (see Q3).

## Q2. Presence and intent binding: WebAuthn UP vs UV, transaction confirmation / WYSIWYS, MFA number matching

### Takeaway
Standards distinguish *presence* (someone touched the device) from *verification* (the right person, through biometric or PIN) from *intent* (they meant this specific transaction). NIST 800-63B-4 now requires a secret to be transferred between channels for out-of-band authentication. Microsoft enforces number matching on all Authenticator pushes. GOV-AIOS's 4-letter code, shown both in the browser and in the Touch ID prompt, follows this pattern. But it is a *compare*-style check, which NIST calls insufficient for OOB authenticators unless the user enters the secret.

### Cited Findings
- **[V]** W3C WebAuthn Level 3 became a W3C Recommendation on 25 Aug 2026. Authentication ceremonies include "a test of user presence or user verification," and an authorization gesture "MAY involve user verification if the employed authenticator is capable." The defined extensions are appid, appidExclude, credProps, prf, and largeBlob. No transaction-authorization extension appears in the ToC. — [W3C TR webauthn-3](https://www.w3.org/TR/webauthn-3/)
- **[U]** WebAuthn authenticator data carries a UP flag (bit 0, user presence) and a UV flag (bit 2, user verified). `userVerification` takes "required" / "preferred" / "discouraged". The Level 1 `txAuthSimple` / `txAuthGeneric` extensions (display-and-sign transaction text) were dropped in Level 2 for lack of authenticator support. — [WebAuthn L2](https://www.w3.org/TR/webauthn-2/); [WebAuthn L1 §10](https://www.w3.org/TR/2019/REC-webauthn-1-20190304/)
- **[U]** W3C Secure Payment Confirmation (SPC) is the surviving browser-native transaction-confirmation pattern. The browser, not the page, displays the payee and amount, and the assertion is bound to them. — [W3C SPC](https://www.w3.org/TR/secure-payment-confirmation/)
- **[U]** FIDO UAF defined a "Transaction Confirmation Display" in which the authenticator displays the transaction text and signs it (WYSIWYS). — [FIDO UAF Authenticator Commands](https://fidoalliance.org/specs/fido-uaf-v1.2-ps-20201020/fido-uaf-authnr-cmds-v1.2-ps-20201020.html)
- **[U]** WYSIWYS as a concept: Landrock & Pedersen, "WYSIWYS? — What you see is what you sign?", Information Security Technical Report 3(2), 1998. The EU PSD2 RTS (Delegated Regulation 2018/389, Art. 5, "dynamic linking") requires the authentication code to be bound to the amount and payee shown to the payer. — [EUR-Lex 2018/389](https://eur-lex.europa.eu/eli/reg_del/2018/389/oj)
- **[V]** NIST SP 800-63B-4 §3.1.3 requires "the transfer of the secret between the out-of-band device and the primary channel" and says "Presenting the claimant with a list of secrets to compare is not sufficient." AAL2 "SHOULD" and AAL3 "SHALL" demonstrate *authentication intent*. Biometrics "SHALL only be used as part of multi-factor authentication with a physical authenticator." A biometric alone is not an authenticator. PAD SHOULD be used for fingerprint. Manual-entry authenticator outputs (e.g. TOTP) "SHALL NOT be considered phishing-resistant." — [NIST HTML](https://pages.nist.gov/800-63-4/sp800-63b.html)
- **[V]** Microsoft Entra number matching: "they see a number. They need to enter that number into the app to complete the approval." Number matching is now enabled for all Authenticator push notifications and users cannot opt out. On the same device, Approve/Deny is allowed because "the prompt only shows on the device that initiated the sign in." — [Microsoft Learn](https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-number-match)
- **[V, secondary for date]** Enforcement began rolling out on 8 May 2023 to counter MFA fatigue. — [BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-enforces-number-matching-to-fight-mfa-fatigue-attacks/amp/); [Sikich](https://www.sikich.com/insight/microsoft-mfa-update-in-may-2023-number-matching/)
- **[V]** CISA fact sheet "Implementing Number Matching in MFA Applications" (dated Oct 2022 by secondary sources). It calls number matching an interim mitigation that is weaker than phishing-resistant MFA. — [CISA PDF](https://www.cisa.gov/sites/default/files/publications/fact-sheet-implement-number-matching-in-mfa-applications-508c.pdf)
- **[U]** Apple LocalAuthentication: `LAContext.evaluatePolicy` with `.deviceOwnerAuthenticationWithBiometrics` returns a boolean to the calling process, and the `localizedReason` string is caller-supplied text shown in the system sheet. Keychain items with `SecAccessControl` `.biometryCurrentSet` instead gate a Secure-Enclave-held key. — [Apple LAContext](https://developer.apple.com/documentation/localauthentication/lacontext); [Apple Platform Security](https://support.apple.com/guide/security/welcome/web)

### Inferences
- In WebAuthn terms, Touch ID in GOV-AIOS is UV (biometric), not merely UP. A bare `LAContext` boolean is not cryptographically bound to the request, though: any code running as the same user that can call the governance daemon's API, or patch it, could spoof the result. A stronger version binds the approval to a Secure Enclave signature over (flow digest || page-file digest || nonce). That is GOV-AIOS's analogue of WebAuthn's signed clientDataJSON challenge. The paper should say which variant is implemented.
- The 4-letter code works like number matching, but in its *compare* form. The user sees the same code in the browser and in the Touch ID sheet and is trusted to check that they match. NIST 800-63B-4 deems compare-style insufficient for OOB authenticators and requires entering the secret. GOV-AIOS can defend its design on two grounds: both displays are on the same machine, and the code goes inside the OS-rendered biometric sheet, much like Microsoft's same-device exception. It should still acknowledge that the human may skip the comparison.
- Binding approvals to the digest of the exact flow and page files is WYSIWYS/dynamic linking applied to agent actions. The approved object is the code-like artifact, not a model-written summary. This is the direct countermeasure to Lies-in-the-Loop.
- The 30-minute TOTP session is NIST-style reauthentication with a session timeout, invalidated when the screen locks. TOTP is manual entry, so it is not phishing-resistant under 800-63B-4 §3.2.5. The paper should rank it below the Touch ID path.

### Gaps
- The exact WebAuthn L3 text for UP/UV definitions and flag bits was not fetched (the page was truncated). Cite §6.1 after checking.
- No academic user study was found that measures how well number matching or compare-code schemes reduce fatigue acceptance.

## Q3. Agent-specific proposals: critiques of approval as a boundary, vendor oversight guidance, delegation and authorization for agents, IETF drafts

### Takeaway
Vendors (Anthropic, OpenAI, Google) all recommend human confirmation for consequential actions, alongside isolation. Recent academic work shifts from "ask the human" toward verifiable delegation: scoped credentials that bind an agent to a human principal, and OAuth extensions for agents acting on a user's behalf. GOV-AIOS sits between the two. Human presence is proven locally per run, and the approval is scoped to a digest-pinned flow, which functions as a local, non-OAuth capability.

### Cited Findings
- **[V]** Anthropic computer-use tool docs recommend: (1) a dedicated VM/container with minimal privileges; (2) no access to sensitive data or credentials; (3) a domain allowlist; (4) "Asking a human to confirm decisions that might result in meaningful real-world consequences and any tasks requiring affirmative consent." When an app asks a human to confirm, "make that check before each block runs, because a batch can complete a multistep action within one turn." — [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- **[V]** OpenAI Operator (Jan 2025): "Before finalizing any significant action, such as submitting an order or sending an email, Operator should ask for approval." There is a takeover mode for logins and payments, and a "watch mode" requiring close supervision on email and financial sites. Operator was later folded into ChatGPT agent mode. — [OpenAI](https://openai.com/index/introducing-operator/)
- **[Gap]** The Operator system card (https://openai.com/index/operator-system-card/) returned 403. Its confirmation and prompt-injection-monitor statistics were not verified.
- **[V]** Díaz, Kern, Olive (Google), "An Introduction to Google's Approach to AI Agent Security" (2025). Three principles: agents must have well-defined human controllers, limited powers, and observable actions and planning. Explicit human confirmation is required for critical or irreversible actions, within a hybrid defense in depth (deterministic plus reasoning-based). — [Google Research](https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/); [Willison summary](https://feeds.simonwillison.net/2025/Jun/15/ai-agent-security/)
- **[V]** South, Marro, Hardjono, Mahari, Whitney, Greenwood, Chan, Pentland, "Authenticated Delegation and Authorized AI Agents," arXiv:2501.09674 (Jan 2025). Users issue signed credentials that identify the AI system and its scoped permissions, built on OAuth 2.0 / OpenID Connect, with an audit trail of which human authorized what. — [arXiv:2501.09674](https://arxiv.org/abs/2501.09674)
- **[V]** IETF individual draft draft-oauth-ai-agents-on-behalf-of-user (Senarath, later with Dissanayaka; -00 May 2025, -02 Aug 2025). It extends the authorization code flow so the agent has its own identity, separate from the client app. The parameter `requested_agent` (-00) became `requested_actor` plus an `actor_token` (-02). PKCE is required. Not adopted by the OAuth WG. — [datatracker -02](https://datatracker.ietf.org/doc/html/draft-oauth-ai-agents-on-behalf-of-user-02)
- **[V]** Chan et al., "Visibility into AI Agents," FAccT 2024, arXiv:2401.13138. It assesses agent identifiers, real-time monitoring, and activity logging. Logging should capture multi-agent interactions, tool use, and delayed or diffuse effects. — [arXiv:2401.13138](https://arxiv.org/abs/2401.13138v6)
- **[U]** Chan et al., "IDs for AI Systems," arXiv:2406.12137; Chan et al., "Infrastructure for AI Agents," arXiv:2501.10114 (attribution, interaction, and response infrastructure).
- **[U]** Debenedetti et al., "Defeating Prompt Injections by Design" (CaMeL), arXiv:2503.18813. Capability-based control and data flow, with user confirmation when a policy would be violated. The authors note that confirmations add user burden.
- **[U]** Beurer-Kellner et al., "Design Patterns for Securing LLM Agents against Prompt Injections," arXiv:2506.08837 (plan-then-execute, action selector, and similar patterns that reduce reliance on per-action approval).

### Inferences
- GOV-AIOS reframes approval from per-action ("may I run this command?") to per-artifact ("may this digest-pinned flow run while I'm present?"). That moves the human decision to a point where the content is deterministic and reviewable. It is closer to CaMeL-style plans or capability grants than to Claude Code-style per-tool prompts, and it sidesteps the 93%-accept problem by asking far less often.
- Compared with South et al. and the IETF OBO draft, GOV-AIOS is single-machine and has no accounts (single admin per laptop). There is no token issuer and no relying party, and the "credential" is the local approval record. The paper should position it as complementary. Its scope is the local presence and intent problem those network-delegation schemes take for granted.

- No IETF WG-adopted agent-auth document was confirmed. Other individual drafts exist (e.g. agent identity and AAuth-style drafts), but they were not verified this session. Search the datatracker for "agent" before final citation.

## Q4. Tamper-evident logging: classic schemes and what a single-machine, same-user hash chain does and does not guarantee; agent audit/observability proposals

### Takeaway
A hash chain on one machine, written by the same user the agent runs as, gives *tamper evidence against partial edits* by someone who doesn't recompute the chain. It gives *no* protection against an adversary with that user's privileges, who can truncate the log, delete it, or rewrite and re-hash the whole chain. The literature closes this gap with forward-secure keys whose earlier keys are erased (Schneier–Kelsey, Bellare–Yee, Ma–Tsudik), and with external commitments, auditors, and gossip (Crosby–Wallach, Certificate Transparency). Agent observability standards (OpenTelemetry GenAI) define *what* to log but not integrity.

### Cited Findings
- **[V]** Schneier & Kelsey, "Secure Audit Logs to Support Computer Forensics," ACM TISSEC 1999, pp. 159–176. Volume and issue are cited inconsistently: Schneier's site gives v.1 n.3, others give 2(2). DOI 10.1145/317087.317089 is **[U]**. The scheme makes entries written *before* compromise of the logging machine unreadable to the attacker and "impossible to undetectably modify or destroy." The goal is detection, not prevention. An earlier version appeared at USENIX Security 1998 as "Cryptographic Support for Secure Logs on Untrusted Machines." — [Schneier](https://www.schneier.com/academic/archives/1999/05/secure_audit_logs_to.html); [1998 PDF](https://www.cs.unc.edu/~fabian/courses/CS600.624/paper-secure-logs.pdf)
- **[U, PDF fetched but unreadable]** Crosby & Wallach, "Efficient Data Structures for Tamper-Evident Logging," USENIX Security 2009. A history tree (Merkle-based) lets an untrusted logger issue commitments, with O(log n) membership and incremental (consistency) proofs. Auditors must keep and compare commitments. Tampering is detectable only relative to a commitment someone outside the logger holds. — [USENIX PDF](https://www.usenix.org/legacy/event/sec09/tech/full_papers/crosby.pdf)
- **[U]** Bellare & Yee, "Forward Integrity for Secure Audit Logs," UCSD TR 1997 (forward-secure MACs). Ma & Tsudik, "A New Approach to Secure Logging," ACM TOS 5(1), 2009, DOI 10.1145/1502777.1502779 (FssAgg, which addresses truncation and deletion). Marson & Poettering, "Practical Secure Logging: Seekable Sequential Key Generators," ESORICS 2013, DOI 10.1007/978-3-642-40203-6_7, the basis of systemd-journald Forward Secure Sealing (`journalctl --setup-keys` / `--verify`).
- **[U]** Certificate Transparency: RFC 6962 (Laurie, Langley, Kasper, 2013) and RFC 9162 (CT v2.0, 2021). Append-only Merkle logs with signed tree heads, inclusion and consistency proofs, and monitors/auditors. Split-view (fork) attacks are detected only by gossip or witness cosigning. Implementations include Google Trillian and witness-cosigned logs such as Sigsum. — [RFC 6962](https://www.rfc-editor.org/rfc/rfc6962); [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162); [Trillian](https://github.com/google/trillian); [Sigsum](https://www.sigsum.org/)
- **[U]** Haber & Stornetta, "How to Time-Stamp a Digital Document," J. Cryptology 3(2), 1991, DOI 10.1007/BF00196791. This is the origin of linked-hash timestamping, and it relies on publishing chain values externally.
- **[V]** OpenTelemetry GenAI semantic conventions have moved to a dedicated repository (open-telemetry/semantic-conventions-genai) covering spans, metrics, and events. No integrity or tamper-evidence provisions were found on the landing page. The agent span names (`create_agent`, `invoke_agent`, `execute_tool`) and the opt-in content capture are **[U]** (from prior knowledge of the conventions). — [OTel notice](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans/); [repo](https://github.com/open-telemetry/semantic-conventions-genai)
- **[V]** Chan et al. (arXiv:2401.13138) and South et al. (arXiv:2501.09674) both call for agent activity logs and audit trails, but neither specifies a tamper-evidence mechanism in the parts read this session. — links above.
- **[U]** Dong, Lu, Zhu, "AgentOps: Enabling Observability of LLM Agents," arXiv:2411.05285 (taxonomy of agent artifacts to trace).

### Inferences: residual risk statement for the paper (GOV-AIOS append-only hash chain plus `verify-audit`)
What it guarantees:
- An edit, insertion, or deletion in the middle of the log, made by a party who does not re-hash every later entry, is detected by `verify-audit`.
- Accidental corruption and casual tampering (editing one JSON line) are detected.
- If someone records the head hash elsewhere (printed, emailed, or committed to git), every prefix up to that head can be verified later. This is the Crosby–Wallach or CT commitment idea with a human or out-of-band witness.

What it does not guarantee:
- **Full rewrite.** An attacker or agent running with the same UID as the log writer can recompute the entire chain. Without a secret key the attacker lacks (keyed MAC or signing key in the Secure Enclave or Keychain behind biometric ACL) or an external anchor, the forged chain verifies.
- **Truncation, tail deletion, and whole-file deletion** are undetectable without an external record of the latest head and length (the Ma–Tsudik truncation problem).
- **No forward security.** If the integrity key, if any, is persistent and readable by the user, compromise lets an attacker re-forge past entries. Schneier–Kelsey and FssAgg evolve and erase keys so that pre-compromise entries stay protected.
- **Forking and split views.** With no auditors or gossip, the machine can show different histories to different verifiers.
- **Garbage in.** The chain proves the integrity of what was logged, not that the logger recorded the truth or recorded everything. A compromised governance daemon can omit events.
- **Timestamps** are local and unauthenticated (no RFC 3161 TSA or external time anchor).
- **Cheap upgrades, in increasing strength:** (a) an HMAC or signature with a Secure Enclave key, so a same-UID attacker without biometric approval can't sign; (b) periodic external anchoring of the head hash (git remote, a transparency log such as Sigsum or Rekor, or a printed receipt); (c) forward-secure key evolution. The paper can list these as future work.
